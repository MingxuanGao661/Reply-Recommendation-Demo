# 端上 LoRA 训练 · 前端对接说明

**文档目的**：给前端同学同步**当前进度与需求**——在哪些业务场景下，需要给训练/推理准备**什么输入**、应预期**什么输出**；不记录后端实现细节（文件路径、类名、bridge 等请直接问 iOS）。

---

## 1. 能力边界（产品预期）

**训练 PoC 目前能做到**

- 在设备上跑一小段 LoRA 微调 smoke test，产出一份 adapter 文件（`.gguf`）。
- 前端传入样本列表；训练过程中通过事件流上报进度、日志、设备状态；结束时给出报告（含 adapter 路径、耗时、错误码等）。

**刻意不做 / 未做全**

- 不做数据清洗与标注质检流水线。
- 训练完成后**不会自动**把新 LoRA接到聊天推理里；需要产品里「选用本次 adapter」的流程（见第 4 节）。
- 长时间后台保活、队列训练等不在 PoC 范围。

---

## 2. 训练：前端需要提供什么、会拿回什么

### 2.1 输入（调用训练时）

| 项目 | 说明 |
|------|------|
| **样本列表** | `String` 数组，每条是一条完整样本字符串。 |
| **纯文本样本** | 任意非 JSON 的字符串：整段原样参与训练（用于简单 smoke）。 |
| **JSONL 单行** | 若整段字符串可被解析为「社交回复数据集」里的一行对象（含 `conversation`、`target.suggestions` 等），后端会按下面 **general / decision** 规则把它变成「对话式训练文本」再参与训练；解析失败则仍当纯文本。 |
| **可选训练参数** | 如上下文长度、epoch 等：与 iOS 同学对齐是否需要自定义；默认即可先跑通。 |

**建议**：先 **5～20 条**、每条尽量短，确认能跑完再加大数据量。

### 2.2 输出（训练过程中与结束后）

| 阶段 | 前端应关注 |
|------|------------|
| **进行中** | 状态机：`idle → running → … → completed / failed`；日志列表；若有 step 指标则展示进度、loss、内存、温度等（字段名与 iOS 类型对齐即可）。 |
| **成功** | **adapter 的绝对路径**（报告里给出，用于「保存到设置 / 选用 personal LoRA」）；总耗时、峰值内存、最后 loss 等便于展示。 |
| **失败** | 错误码 + 最近若干条日志，便于用户反馈与排障。 |

**路径**：不要写死沙盒路径；**以后端/报告返回的路径为准**。

**约束**：训练**不要在主线程**触发；设备可能发热，温度到较高档时建议提示用户。

**错误码（用户可见文案）**：`0` 成功；非 `0` 时常见为模型加载失败、上下文过大、**数据太短**、训练初始化失败、保存失败等——详细枚举问 iOS。

## 3. 训练数据：一行 JSON 算「哪种题」、后端期望里有什么

当前与数据集 schema 对齐时，**每一行**可按下面规则分为两类（与训练侧分支一致，便于你们做导入校验或提示文案）：

| 条件（行内字段） | 类型 |
|------------------|------|
| `task_type == "decision"` **或** `suggestion_theme == "decisionReply"` | **decision** |
| 否则 | **general**（含 `from_scratch`、`rewrite` 等） |

**对「这一行在练什么」的约定（给产品/数据同学）**

| 类型 | 训练里模型被教成输出什么 | 数据上建议 |
|------|--------------------------|------------|
| **general** | **一条**自然短信式回复（纯文本），不是 `{"suggestions":[...]}` 三卡菜单。 | 若有明确「用户最想发的一句」，建议在 `target` 里提供 **`primary_text`**（字符串）；没有时后端会用固定启发从 `target.suggestions` 里占位一条主推荐（顺序 **`Friendly` → `Direct` → `Thoughtful`** …），**仍建议尽量写 `primary_text`** 以免和真实偏好偏差。 |
| **decision** | **三条**立场，且为紧凑 **JSON**，与现有产品里的 `suggestions` 形状一致：`Agree`、`Soft Decline`、`Delay` 各一条 `text`。 | `target.suggestions` 三条标签齐全即可。 |

前端若做「从文件读入训练」：**按行 append 到样本数组即可**，不必在客户端拼训练用中间文件。

## 4. Personal / User LoRA（训练产物）与默认 LoRA

**产品语义**

- **默认 LoRA**：App 里自带的 bundle 适配器（与设置里「Reply SFT LoRA」一类开关对应）。
- **Personal / User LoRA**：用户用本次（或某次）训练报告里的路径，选用**自己设备上训出来的** adapter。

**互斥（已由 iOS 处理）**

- 打开 **User / personal LoRA** 时，**默认 bundled LoRA 会自动关掉**（避免两个叠在一起）。
- 用户再打开默认 LoRA 时，会关掉 User LoRA 一侧（二选一）。

**训练成功后，前端需要配合的流程**

1. 从训练成功报告里取出 **adapter 文件路径**。
2. 写入「选用 personal LoRA」所需配置（路径 + 开关）；具体 **UserDefaults key 或与 `AppSettingsStore` 的绑定** 问 iOS，本文不写死实现名。
3. 写入后本地聊天引擎会按新配置重建（无需用户重启 App 的硬性要求，以 iOS 行为为准）。

## 5. 推理侧契约：什么时候要「一种输入、一种输出」

以下描述的是**产品应对齐的 I/O 约定**（与当前训练数据 general/decision 一致）。

**iOS 已实现**：当 **`userTrainedLoraAdapterEnabled` 为真且用户 adapter 路径有效**（即 personal / User LoRA 实际生效）且当前线程为 **general（`replyStyles`）** 时，本地推理会**自动**改用「单条纯文本」专用 prompt，并把结果规整为 **一条** `Suggestion`（标签为 `Natural`，便于沿用现有归一化逻辑）。**decision** 仍为原有三立场 JSON，不切换。

前端只需按下面矩阵做 **UI 展示**（例如 general + personal 时是否仍摆三卡位、只显示一条等）；**不必**再自行切换发给模型的 prompt 字符串。

### 5.1 矩阵（前端展示与预期的依据）

| 设置 | 会话类型 | 模型侧期望输出形态（已由 iOS 对齐） | 前端解析 / UI |
|------|-----------|--------------------------------------|----------------|
| **未使用** personal LoRA | **general** | **三语气** JSON（`Direct` / `Friendly` / `Thoughtful`） | 沿用现有三卡 UI 与解析 |
| **使用** personal LoRA | **general** | **一条**自然短信（内部再包成单卡 JSON，标签 `Natural`） | **单条推荐**：通常只展示一条即可；若 UI 仍保留三卡位，需产品决定（例如只填第一卡或隐藏余下两卡） |
| 任意 | **decision** | **三条**立场 JSON（`Agree` / `Soft Decline` / `Delay`） | 沿用现有三卡解析 |

### 5.2 如何区分 general / decision（与训练一致）

与第 3 节表格相同：由业务根据当前会话 / `ConversationInput` 是否属于「要二选一、邀请、去不去」等 **decision** 场景分支；否则为 **general**。

---

## 6. 训练 UI：状态与展示建议（可选）

- **进行中**：`running`，展示 `runID`、日志、若有 step 则展示进度与 loss、内存、温度、前后台提示。
- **成功**：`completed`，必显 **adapter 路径**、耗时、峰值内存、最终 loss（若有）。
- **失败**：`failed`，错误码 + 日志片段。

---

## 7. 仍须与 iOS 对齐的清单（本文不展开实现）

- 训练 API 的准确方法签名、事件与 `Report` 的字段类型。
- personal LoRA 开关与路径在设置里的**唯一绑定方式**（若设置 UI 尚未接好，问 iOS 要绑定字段名）。
