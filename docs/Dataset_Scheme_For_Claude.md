# Dataset Scheme for Claude Distillation (SFT)
**Target Model:** Llama 3.2 3B Instruct (SFT via Unsloth)  
**Task:** Social Reply Generation — 3 suggestions (Direct / Friendly / Thoughtful **or** Agree / Soft Decline / Delay)  
**Distillation Source:** Claude  
**Format:** JSONL — raw data layer + training messages layer  
**Last updated:** April 2026 — synced with `PromptBuilder.swift` + `Models.swift`; §4.0 / §5 quality constraints; §2.0 / §5 optional `distillation_controls` for generation

---

## 1. Design Principles

- **SFT = imitation**: The model learns to produce the same output Claude would. No scoring, no consequence evaluation — that belongs to GRPO.
- **Mirror the app exactly**: Core fields map 1-to-1 to `ConversationInput` in `Models.swift`. Optional `distillation_controls` (§2.0) is the only documented extension for generation; it is not an app input.
- **Three task types**: `from_scratch` (no draft), `rewrite` (has draft), `decision` (yes/no binary prompt, no draft). See section 3.
- **Two suggestion themes**:
  - `replyStyles` → labels `Direct`, `Friendly`, `Thoughtful`
  - `decisionReply` → labels `Agree`, `Soft Decline`, `Delay`
- **Speaker = real user ID**: `"me"`, `"alice"`, `"bob"` etc. Display names are resolved at prompt-build time via `participants`.
- **conversation**: Max **10 turns**, average target **4–6 turns**. Truncate from the front if needed.
- **Distillation-only knobs**: Optional `distillation_controls` (§2.0) steers Claude during generation. It does **not** mirror the app runtime API; you may **omit** it from raw rows, **strip** it when exporting strict app-parity training messages, or **keep** it in metadata-only pipelines for analysis.

## 2. Raw JSONL Schema (Data Layer)

This is what you save, label, and clean. Generated by calling Claude with the same prompts the app uses.

### 2.0 Distillation-only hidden controls (optional)

Top-level object **`distillation_controls`** — use **only** at Claude generation time (and optionally persist on raw JSONL for provenance / stratified sampling). **Not** required for schema validation, **not** part of `ConversationInput`, and **not** assumed present at app inference.

| Key | Type | Allowed values |
|-----|------|------------------|
| `scene_tag` | string | `awkward` · `soft_interest` · `delay` · `reconnect` · `casual_warmth` |
| `social_risk` | string | `low` · `medium` · `high` |
| `relationship_distance` | string | `close` · `medium` · `distant` |

**Semantics (short):**

- **`scene_tag`** — situational vibe of the last turn / thread slice (not the suggestion label `Delay` in `decisionReply`; that remains the output slot name only).
- **`social_risk`** — how costly a wrong tone might feel (`high` = tighter calibration, fewer glib lines).
- **`relationship_distance`** — psychological closeness between Me and `reply_to` for this beat (orthogonal to `participants[].relationship` labels like `friend` / `manager`).

**Example fragment** (any task type / theme; omit keys you do not need):

```json
"distillation_controls": {
  "scene_tag": "reconnect",
  "social_risk": "medium",
  "relationship_distance": "close"
}
```

**Prompt placement:** merge into the **user** turn (append before `Reply in JSON as instructed.`), not into the app’s system prompt mirror — keeps shipping `PromptBuilder` unchanged and makes “strip for strict SFT” a single delete of that suffix.

## 3. Field Reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `sample_id` | string | ✅ | Unique ID, e.g. `social_000001` |
| `task_type` | enum | ✅ | `from_scratch` / `rewrite` / `decision` |
| `suggestion_theme` | enum | ✅ | `replyStyles` / `decisionReply` — determines which label set is used |
| `self_id` | string | ✅ | Speaker ID for "me", typically `"me"` |
| `participants` | list | ✅ | Each entry: `id`, `name`, `is_self`, `relationship` |
| `participants[].relationship` | string | ⚪ | `friend` / `classmate` / `manager` / `colleague` / `romantic_interest` / `acquaintance` |
| `conversation` | list | ✅ | Each entry: `speaker` (user ID), `text`. Max **10 turns**, target **4–6** |
| `reply_to` | string | ⚪ | Speaker ID of who we're replying to. Null = last message |
| `conversation_profile.tone` | string | ✅ | e.g. `casual`, `warm`, `professional`, `direct` |
| `conversation_profile.length` | string | ✅ | `short` / `medium` / `long` |
| `draft` | string | ✅ | Empty string `""` for `from_scratch` / `decision`; user's partial text for `rewrite` |
| `target.suggestions` | list | ✅ | Exactly 3 items. Labels depend on `suggestion_theme` — see section 4.3 |
| `metadata.source` | string | ✅ | `claude_distilled` / `human_written` / `claude_distilled_human_filtered` |
| `metadata.split` | enum | ✅ | `train` / `val` / `test` |
| `metadata.format_validated` | bool | ✅ | Must be `true` before adding to training set |
| `distillation_controls` | object | ⚪ | **Generation / raw JSONL only** — see §2.0. Keys: `scene_tag`, `social_risk`, `relationship_distance` (each optional inside the object). Strip when building strict app-parity `messages` if you do not want the student to see controls. |

> **`conversation_profile` not `profile`** — this matches `ConversationInput.CodingKeys` in `Models.swift`. Using `"profile"` will silently break JSON parsing (field ignored, tone/length fall back to defaults).

## 4. Training Messages Format (Llama 3.2 / Unsloth)

Converted from raw JSONL using the same logic as `PromptBuilder.swift`. System and user prompts must be constructed identically to what the app sends at inference time.

**Distillation / SFT note:** For Claude calls and for training-message `system.content`, append the block below **after** the mirrored app system text (same placement as `{quality_constraints}` in section 5). This tightens voice and differentiation beyond what the shipping app prompt currently encodes.

**Optional `distillation_controls`:** If present on the raw sample, append the human-readable control block to the **user** message for the Claude call (see §5). For **strict** train-on-app-distribution-only exports, delete that suffix from `user.content` so the student never conditions on hidden tags; for **controlled** curricula, you may leave it in during an intermediate stage (document which pipeline you use).

### 4.0 Additional quality constraints (system prompt supplement)

Use verbatim (English) for all outputs, all themes (`replyStyles` and `decisionReply`), all task types:

```
Additional quality constraints for all outputs:

- Write like a real young person texting, not like a polished assistant.
- Keep replies sendable. Do not optimize for being impressive.
- Avoid sounding overly emotionally intelligent, overly careful, or therapist-like.
- Avoid generic polished lines that could fit any context.
- Avoid over-explaining, over-validating, or wrapping a simple answer in too much softness.
- "Friendly" should feel warmer, not just noisier or more full of filler like "haha". **Style-heavy** slang (ngl, fr, tbh, lowkey, bet, …) belongs mainly on **Friendly** — use lightly, not stacked. **Direct** / **Thoughtful**: no style-heavy slang; at most **one** ultra-light abbreviation (idk, rn, lmk) per line when natural.
- "Thoughtful" should feel slightly more context-aware, not longer, not more formal, and not a reflective paragraph.
- "Direct" should be concise and clear, but not cold or blunt unless the context truly calls for it.
- The three outputs must feel noticeably different in strategy, not just wording.
- One message, one move: do not stack multiple social jobs in a single reply.
- Never do all at once: reassurance + analysis + proposal + future outlook; pick one beat per line.
- Do not explain more than this thread actually requires.
- Do not spell out subtext or "read the room" out loud; leave some implicit.
- Never pad length to sound Thoughtful; Thoughtful is slightly more anchored, not longer.
- Do not sound like a polished "high-EQ example answer" or social-skills coaching script.
- Abbreviations and light youth/internet phrasing are fine when they fit the relationship and thread — keep it readable and sendable; do not pile on slang, forced letter-dropping, or a performative very-online voice. (`replyStyles`: **Friendly** may use style-heavy markers sparingly; **Direct** / **Thoughtful** only idk/rn/lmk, at most one each; **`decisionReply`**: readable, no style-heavy pile-on.)
- Avoid canned polite templates like "I'd love to", "Looking forward to it", "Sorry to miss it", "double-check my calendar", "by end of day", "at your earliest convenience".
- Avoid email/HR phrasing. Keep it spoken-text natural, not corporate polished.
- For `decisionReply`, keep outputs short and asymmetric in rhythm; do not make all three the same sentence length/style.
- For `replyStyles`, do not pack attitude + long explanation + boundary + next step into one message; often one clause is enough.
- For `replyStyles` **Thoughtful**: keep very short (e.g. ≤18 words), one sentence, at most one comma; avoid therapist-y reflection and tidy closure.
- No blind guessing: do not invent specific facts (time/place/reason) that are not supported by the conversation.
- Use a detail budget by `social_risk`: `high` = 0 new concrete details, `medium` = <=1, `low` = <=2.
- If context is underspecified, prefer safe brevity over adding speculative backstory.
- Do not use emoji in suggestions.
- Do not use hyphen/dash punctuation in suggestions (avoid both "-" and "—").
- Prefer natural brevity. If one sentence works, do not make it three.
```

For `decisionReply`, interpret the guidance on strategic difference, youthful phrasing (including abbreviations / light slang — in moderation), no emoji/no dash punctuation, and brevity in spirit: **Agree** / **Soft Decline** / **Delay** must differ in *stance and strategy*, stay sendable and human, and avoid therapist-y or generic polish.

### 4.1 `from_scratch` / `replyStyles` example

**Raw data input:**
- `conversation_profile`: `{tone: "casual", length: "short"}`, no personal profile override
- `reply_to`: `"alice"`, last message: `"all good? haven't heard from you in a bit"`

```json
{
  "messages": [
    {
      "role": "system",
      "content": "Suggest 3 texts Me can send. Answer the OTHER person's last message.\n\n- Style — honor BOTH the user's personal preferences AND this conversation's settings:\n  • Personal (user, app-wide): tone: not set (no personal preference on this axis) | length: not set (no personal preference on this axis)\n  • This conversation / thread: tone: casual | length: short\n  • Use for THIS reply (per axis: conversation value if set, else personal, else app default warm/short): Tone: casual | Length: short\n- Three reply styles — all replying to the LAST message only; each must feel NOTICEABLY different:\n  • Direct    = lead with the answer right away; skip warm-ups and filler; shorter is better\n  • Friendly  = add one warm or personal touch to YOUR ANSWER (their name, \"haha\", \"for sure\"); don't recap the conversation\n  • Thoughtful = briefly acknowledge the specific question or situation in the last message, then give your reply\n\nRules:\n- Address Alice's message directly. ### 4.5 Assistant Output Format Rules
```

**`replyStyles` theme** — assistant turn shape:
```json
{"suggestions": [
  {"label": "Direct",     "text": "..."},
  {"label": "Friendly",   "text": "..."},
  {"label": "Thoughtful", "text": "..."}
]}
```

**`decisionReply` theme** — assistant turn shape:
```json
{"suggestions": [
  {"label": "Agree",        "text": "..."},
  {"label": "Soft Decline", "text": "..."},
  {"label": "Delay",        "text": "..."}
]}
```

Hard-filter rules before adding to training set:

- [ ] Valid JSON (parseable)
- [ ] `suggestions` key exists and is an array of exactly 3 items
- [ ] Labels exactly match the expected set for the sample's `suggestion_theme` (order-insensitive)
- [ ] No markdown fences (` ```json `) wrapping the output
- [ ] No label has empty `text`
- [ ] All 3 texts are distinct in **strategy** (reject if stripped-of-punctuation/filler texts are pairwise too similar; for `replyStyles`, also reject if Direct/Friendly/Thoughtful **first clauses** are near-duplicates)
- [ ] For `decisionReply`: reject if all 3 texts are positive/accepting variants (no real soft decline or delay)

## 5. Claude Distillation Prompt

When calling Claude to generate `target.suggestions`, use the **same system + user prompts** that `PromptBuilder.swift` produces for the same input, **plus** the `QUALITY_CONSTRAINTS` block from section 4.0 (inserted as in the Python templates below). At inference time the app may still use the shorter system prompt only; the extra block is the documented distillation / SFT supplement so labels stay human and strategically distinct.

If the raw row carries **`distillation_controls`** (§2.0), append **`build_distillation_controls_user_suffix(sample)`** to the **user** message immediately before `Reply in JSON as instructed.` — not to the system string. Strip that suffix when exporting strict app-parity training pairs.

Python mirror of `PromptBuilder.swift`:

```python
THEME_RULES = {
    "replyStyles": (
        "- Three reply styles — all replying to the LAST message only; each must feel NOTICEABLY different:\n"
        "  • Direct    = lead with the answer right away; skip warm-ups and filler; shorter is better\n"
        "  • Friendly  = add one warm or personal touch; style-heavy slang sparingly; Direct/Thoughtful: no style-heavy, at most one ultra-light (idk, rn, lmk); don't recap the conversation\n"
        "  • Thoughtful = briefly acknowledge the specific question or situation in the last message, then give your reply"
    ),
    "decisionReply": (
        "- Three decision stances — all replying to the LAST message; each must give a clearly different answer:\n"
        "  • Agree       = clear yes / direct acceptance; no hedging\n"
        "  • Soft Decline = kind no — warm but firm; don't over-explain\n"
        "  • Delay       = defer without committing — ask for more time or say you'll confirm later"
    ),
}

LABEL_LISTS = {
    "replyStyles":   '"Direct", "Friendly", "Thoughtful"',
    "decisionReply": '"Agree", "Soft Decline", "Delay"',
}

# Append to system prompt for distillation / training (section 4.0). Not in shipping PromptBuilder.swift yet.
QUALITY_CONSTRAINTS = """\
Additional quality constraints for all outputs:

- Write like a real young person texting, not like a polished assistant.
- Keep replies sendable. Do not optimize for being impressive.
- Avoid sounding overly emotionally intelligent, overly careful, or therapist-like.
- Avoid generic polished lines that could fit any context.
- Avoid over-explaining, over-validating, or wrapping a simple answer in too much softness.
- "Friendly" should feel warmer, not just noisier or more full of filler like "haha". **Style-heavy** slang (ngl, fr, tbh, lowkey, bet, …) belongs mainly on **Friendly** — use lightly, not stacked. **Direct** / **Thoughtful**: no style-heavy slang; at most **one** ultra-light abbreviation (idk, rn, lmk) per line when natural.
- "Thoughtful" should feel slightly more context-aware, not longer, not more formal, and not a reflective paragraph.
- "Direct" should be concise and clear, but not cold or blunt unless the context truly calls for it.
- The three outputs must feel noticeably different in strategy, not just wording.
- One message, one move: do not stack multiple social jobs in a single reply.
- Never do all at once: reassurance + analysis + proposal + future outlook; pick one beat per line.
- Do not explain more than this thread actually requires.
- Do not spell out subtext or "read the room" out loud; leave some implicit.
- Never pad length to sound Thoughtful; Thoughtful is slightly more anchored, not longer.
- Do not sound like a polished "high-EQ example answer" or social-skills coaching script.
- Abbreviations and light youth/internet phrasing are fine when they fit the relationship and thread — keep it readable and sendable; do not pile on slang, forced letter-dropping, or a performative very-online voice. (`replyStyles`: **Friendly** may use style-heavy markers sparingly; **Direct** / **Thoughtful** only idk/rn/lmk, at most one each; **`decisionReply`**: readable, no style-heavy pile-on.)
- Avoid canned polite templates like "I'd love to", "Looking forward to it", "Sorry to miss it", "double-check my calendar", "by end of day", "at your earliest convenience".
- Avoid email/HR phrasing. Keep it spoken-text natural, not corporate polished.
- For `decisionReply`, keep outputs short and asymmetric in rhythm; do not make all three the same sentence length/style.
- For `replyStyles`, do not pack attitude + long explanation + boundary + next step into one message; often one clause is enough.
- For `replyStyles` **Thoughtful**: keep very short (e.g. ≤18 words), one sentence, at most one comma; avoid therapist-y reflection and tidy closure.
- No blind guessing: do not invent specific facts (time/place/reason) that are not supported by the conversation.
- Use a detail budget by `social_risk`: `high` = 0 new concrete details, `medium` = <=1, `low` = <=2.
- If context is underspecified, prefer safe brevity over adding speculative backstory.
- Do not use emoji in suggestions.
- Do not use hyphen/dash punctuation in suggestions (avoid both "-" and "—").
- Prefer natural brevity. If one sentence works, do not make it three."""

SYSTEM_NO_DRAFT = """\
Suggest 3 texts Me can send. Answer the OTHER person's last message.

{style_block}
{theme_rules}

{quality_constraints}

Rules:
- Address {reply_target} directly. If they asked a question, answer it; do not only repeat what they said.
- Obey the Style rules above. Short, casual, real person texting unless length is long. Avoid unnecessary exclamation marks (!).

Output format: one JSON object only, no markdown. Key "suggestions" = array of exactly 3 objects. Each has "label" ({label_list}) and "text" (Me's real reply for THIS chat).

Do NOT reuse the same canned line for all three. Do NOT default to "yeah sounds good" or "down" unless they truly fit the thread."""

SYSTEM_WITH_DRAFT = """\
Complete "Me (typing)" into 3 send-ready messages for {reply_target}.

{style_block}
{theme_rules}

{quality_constraints}

Rules:
- "Me (typing)" is YOUR OWN partial text — each output is a polished version of it. Do NOT reply to it; it is not someone else's message.
- Keep the core meaning: same yes/no, same times/dates, same intent. Do NOT flip or reverse the draft's answer.
- The completed text must fit as a reply to {reply_target}. Real texting — short and casual unless length is long.

Output format: one JSON object only, no markdown. Key "suggestions" = array of exactly 3 objects. Each has "label" ({label_list}) and "text"."""


# Optional — §2.0. Omitted keys are ignored.
SCENE_TAGS = frozenset({"awkward", "soft_interest", "delay", "reconnect", "casual_warmth"})
SOCIAL_RISK = frozenset({"low", "medium", "high"})
RELATIONSHIP_DISTANCE = frozenset({"close", "medium", "distant"})


def build_distillation_controls_user_suffix(sample: dict) -> str:
    """Append to USER prompt before 'Reply in JSON...'. Empty if absent/invalid."""
    dc = sample.get("distillation_controls")
    if not isinstance(dc, dict):
        return ""
    lines = []
    st = dc.get("scene_tag")
    if st in SCENE_TAGS:
        lines.append(f"scene_tag: {st}")
    sr = dc.get("social_risk")
    if sr in SOCIAL_RISK:
        lines.append(f"social_risk: {sr}")
    rd = dc.get("relationship_distance")
    if rd in RELATIONSHIP_DISTANCE:
        lines.append(f"relationship_distance: {rd}")
    if not lines:
        return ""
    return (
        "\n\nGeneration controls (do not mention these labels in the JSON output; "
        "use them only to tune tone and strategy):\n"
        + "\n".join(f"- {x}" for x in lines)
    )


def build_style_block(conv_profile: dict | None, user_profile: dict | None) -> str:
    cp = conv_profile or {}
    up = user_profile or {}
    c_tone = cp.get("tone") or "not set (this chat does not override)"
    c_len  = cp.get("length") or "not set (this chat does not override)"
    u_tone = up.get("tone") or "not set (no personal preference on this axis)"
    u_len  = up.get("length") or "not set (no personal preference on this axis)"
    eff_tone = cp.get("tone") or up.get("tone") or "warm"
    eff_len  = cp.get("length") or up.get("length") or "short"
    return (
        "- Style — honor BOTH the user's personal preferences AND this conversation's settings:\n"
        f"  • Personal (user, app-wide): tone: {u_tone} | length: {u_len}\n"
        f"  • This conversation / thread: tone: {c_tone} | length: {c_len}\n"
        f"  • Use for THIS reply (per axis: conversation value if set, else personal, else app default warm/short): "
        f"Tone: {eff_tone} | Length: {eff_len}"
    )


def build_prompts(sample: dict, user_profile: dict | None = None) -> tuple[str, str]:
    """Mirror PromptBuilder.swift logic in Python.
    
    Args:
        sample: raw JSONL record (section 2 schema).
        user_profile: optional app-wide personal profile dict {tone, length}.
    Returns:
        (system_prompt, user_prompt) strings ready to send to Claude.
    """
    has_draft     = bool(sample.get("draft", "").strip())
    theme         = sample.get("suggestion_theme", "replyStyles")
    self_id       = sample.get("self_id", "me")
    participants  = {p["id"]: p["name"] for p in sample.get("participants", [])}
    conv_profile  = sample.get("conversation_profile")  # NOT "profile"
    reply_to_id   = sample.get("reply_to")
    reply_to_name = participants.get(reply_to_id) if reply_to_id else None

    style_block  = build_style_block(conv_profile, user_profile)
    theme_rules  = THEME_RULES[theme]
    label_list   = LABEL_LISTS[theme]
    reply_target = f"{reply_to_name}'s message" if reply_to_name else "the last message in the conversation"

    # --- System prompt ---
    tmpl = SYSTEM_WITH_DRAFT if has_draft else SYSTEM_NO_DRAFT
    system = tmpl.format(
        style_block=style_block,
        theme_rules=theme_rules,
        quality_constraints=QUALITY_CONSTRAINTS,
        label_list=label_list,
        reply_target=reply_target,
    )

    # --- User prompt ---
    lines = []

    # Group chat header (mirrors isGroupChat: unique speakers > 2)
    unique_speakers = set(m["speaker"] for m in sample["conversation"])
    if len(unique_speakers) > 2:
        others = [p["name"] for p in sample["participants"] if not p.get("is_self")]
        lines.append(f"Group chat with: {', '.join(others)}")
        lines.append("")

    lines.append("Conversation:")
    for msg in sample["conversation"]:
        name = "Me" if msg["speaker"] == self_id else participants.get(msg["speaker"], msg["speaker"])
        lines.append(f"  {name}: {msg['text']}")

    if has_draft:
        # Draft is embedded in conversation as Me's in-progress turn.
        lines.append(f"  Me (typing): \"{sample['draft'].strip()}\"")
        lines.append("")
        if reply_to_name:
            lines.append(f"Complete \"Me (typing)\" into a ready-to-send reply to {reply_to_name}.")
        else:
            lines.append("Complete \"Me (typing)\" into a ready-to-send reply.")
    else:
        # Pin the exact message being replied to.
        target_msg = next(
            (m for m in reversed(sample["conversation"]) if m["speaker"] == reply_to_id),
            sample["conversation"][-1] if sample["conversation"] else None,
        )
        target_name = reply_to_name or "them"
        if target_msg:
            lines.append(f"\nReply ONLY to this message from {target_name}: \"{target_msg['text']}\"")
        elif reply_to_name:
            lines.append(f"\nReplying to: {reply_to_name}")
        lines.append("(no draft — write a fresh reply)")

    lines.append(build_distillation_controls_user_suffix(sample))
    lines.append("\nReply in JSON as instructed.")
    return system, "\n".join(lines)
```

## 6. Dataset Diversity Targets

### Task type split

| `task_type` | Target % |
|---|---|
| `from_scratch` | 50% |
| `rewrite` | 30% |
| `decision` | 20% |

### Suggestion theme split

| `suggestion_theme` | Target % |
|---|---|
| `replyStyles` | 75% |
| `decisionReply` | 25% |

### Relationship coverage

| Relationship | Target % |
|---|---|
| `friend` | 30% |
| `classmate` | 20% |
| `manager` / `colleague` | 20% |
| `romantic_interest` | 15% |
| `acquaintance` | 15% |

### Chat type coverage

| Type | Target % | Trigger condition |
|---|---|---|
| 1-on-1 | 80% | 2 unique speakers in `conversation` |
| Group (3+ people) | 20% | 3+ unique speakers in `conversation` |

### Profile coverage

- `conversation_profile.tone`: cover `casual`, `warm`, `professional`, `direct` — avoid >50% in any single value
- `conversation_profile.length`: roughly 50% `short`, 35% `medium`, 15% `long`

### `distillation_controls` coverage (when used)

Only applies to batches that emit `distillation_controls` on raw JSONL. Rough targets so `scene_tag` / `social_risk` / `relationship_distance` do not collapse to one mode:

| Axis | Values | Suggested spread (each value) |
|------|--------|-------------------------------|
| `scene_tag` | 5 enums | 15–25% each (tweak if a tag is rare in natural threads) |
| `social_risk` | low / medium / high | ~35% / 45% / 20% |
| `relationship_distance` | close / medium / distant | ~40% / 40% / 20% |

Correlate weakly with `participants[].relationship` and thread content — avoid always mapping e.g. `manager` → `distant` + `high` (reduces diversity).

## 7. Conversation History Guidelines

- **Max turns**: 10 (hard cap)
- **Recommended average**: 4–6 turns
- **Truncation**: If raw history > 10 turns, keep the **most recent 10** (drop from the front)
- **Never pad**: Do not invent messages if only 1–2 turns exist
- **Last message** in `conversation` should be the message being replied to (from the other person / a group member)
- **Group chat**: include at least 2 different non-self speakers; ensure the `reply_to` speaker has at least one message in the window

## 8. Minimum Viable Schema (v1 Quickstart)

For the first generation batch, only these fields are strictly required:

```
sample_id
task_type
suggestion_theme
self_id
participants          (id + name + is_self; relationship optional)
conversation          (≤ 10 turns)
reply_to
conversation_profile  (tone + length)   ← NOT "profile"
draft                 (empty string if from_scratch / decision)
target.suggestions    (3 items, labels must match suggestion_theme)
metadata.source
metadata.split
metadata.format_validated
```

Optional for **generation / stratification only** (§2.0): `distillation_controls` — omit from strict SFT export `messages` if you do not want the LM to learn from tagged controls.

## 9. SFT vs GRPO — What Goes Where

| | SFT (this schema) | GRPO (future) |
|---|---|---|
| **Goal** | Imitate Claude's output format and quality | Learn which reply is socially better |
| **Labels needed** | None — just Claude's output | Reward signal: warmth, consequence, naturalness |
| **Consequence field** | ❌ Not needed | ✅ Add here |
| **Scoring** | ❌ Not needed | ✅ Pairwise ranking or scalar reward |
| **Schema complexity** | Minimal | Extended from this schema |

Consequence estimation and scoring should be designed as a **separate GRPO dataset schema** built on top of this one when the time comes.
